# 게임 실행 버튼 상태 개편 계획

작성 기준: 2026-10-06, 현재 HEAD `0f66f4d`.
레이아웃 개편 전 비교 기준: `fa89e01` (`12ec6db`의 부모 커밋).
1~7장은 구현 전 조사 및 승인된 계획이다. 구현 결과와 검증 범위는 8장에 기록한다.

## 1. 개편 전 동작과 현재 빠진 연결

개편 전 `GersangStation.WinUI/GersangStation/Main/StationPage.xaml`은 세 실행 버튼에 `ClientNButtonEnabled`, `ClientNStatusText`를 바인딩했다. `Starting`에는 “켜는 중”, `Running`에는 “실행 중”을 표시했고, `Starting` 슬롯에는 별도의 X 취소 버튼을 표시했다.

- 하나의 슬롯이 `Starting`이면 세 실행 버튼을 모두 비활성화했다. 진행 중인 슬롯의 별도 취소 버튼은 사용할 수 있었다.
- `Running`, `RetryCooldown`, 다클라 미사용 슬롯도 실행 버튼을 비활성화했다.
- 취소 버튼은 `CancelClientStart` → `WebViewManager.CancelLaunchAttempt`로 연결됐다.
- 실행 상태와 판정 로직 대부분은 현재 [HomePage.xaml.cs](../GersangStation/Pages/HomePage.xaml.cs)에 남아 있다. 현재 [SidebarView.xaml](../GersangStation/Controls/SidebarView.xaml)의 실행 버튼은 play 아이콘과 클릭 이벤트만 연결되어 있고, 상태 바인딩과 취소 경로가 없다.
- `HandleClientExecuteAsync`는 실제 슬롯이 `Starting`/`Running`이면 실행 요청을 반환하므로 모든 클릭이 실제 실행으로 이어지는 것은 아니다. 하지만 사이드바에는 그 상태가 보이지 않는다.
- HomePage는 숨겨질 때 `DetachGameStarter`를 호출한다. 사이드바는 BrowserPage에서도 보이므로 기존 HomePage 이벤트 구독을 그대로 이용하면 페이지 전환 후 버튼 상태가 갱신되지 않는다.

## 2. 기존 실행 완료·종료·실패 판단

[WebViewManager.cs](../GersangStation/Services/WebViewManager.cs)가 로그인, OTP, 로컬 소켓 payload 수신을 담당하고, [GameStarter.cs](../GersangStation/Services/GameStarter.cs)가 슬롯 예약, `Run.exe` 실행, 게임 프로세스 추적을 담당한다.

1. 사전 검증: 계정/비밀번호, 경로, 패치 필요 여부, 최대 3클라이언트, 서버를 넘는 동일 계정 중복을 검사한다.
2. `TryBeginStart`가 슬롯을 `Starting`으로 예약한다.
3. 로그인과 필요한 OTP를 처리하고, 127.0.0.1:1818 소켓에서 실행 payload를 받는다. 소켓 대기 제한은 10초다.
4. `Run.exe`를 실행한 뒤 새 `Gersang.exe`의 시작 시각·설치 경로·기존 PID 여부를 검사한다.
5. 유효한 세션에 게임 PID를 연결하는 `PromoteSessionToRunning`이 실제 실행 완료 판단이다. 로그인 성공이나 `Run.exe` 실행만으로 완료 처리하지 않는다.
6. 게임 PID 종료를 1초 주기로 확인하고 세션을 제거하면 슬롯이 다시 사용 가능해진다.
7. 런처가 종료되고 5초의 탐색 유예에도 게임을 찾지 못하면 실행 실패로 세션을 제거한다.

`TryGameStart()`의 `true`는 로그인/실행 요청을 접수·진행했다는 의미다. `GameStarter.StartAsync()`도 게임 탐색 종료 후 `true`를 반환하는 경로가 있어 반환값만으로 실행 완료를 표시해서는 안 된다.

기존 실패 조건도 유지한다. 무한 로그인 감지는 “로그인 폼 제출 후 다시 메인 페이지에 돌아왔지만 비로그인인 경우”다. 계정/비밀번호 오류, 인증 제한, IP 차단, OTP 취소/직접 입력, 점검 페이지, 브라우저 초기화·탐색·프로세스 실패, 소켓 시간 초과/잘못된 payload, 런처 실행 실패/UAC 취소, 게임 시작 감지 실패도 기본 상태 복귀 경로에 포함한다. OTP 오류 후 재입력처럼 기존에 계속 진행하던 경우는 실패 종료로 바꾸지 않는다.

## 3. 버튼 표시와 클릭 계약

| 표시 상태 | 버튼 내용 | 활성 여부 | 클릭 동작 | 종료 조건 |
|---|---|---|---|---|
| 기본 | 기존 play `FontIcon` (`E768`) | 기존 실행 제한 안에서 활성 | 실행 시도 시작 | 유효한 요청을 수락하면 처리 중 |
| 처리 중 | animated `ProgressRing` | 해당 슬롯은 활성 | 해당 실행 시도 취소 | 실행 완료, 취소, 실패 |
| 실행 중 | `FontIcon` (`F0B9`) | 비활성 | 없음 | 해당 게임 프로세스 종료 |

- 기본 → 처리 중 전환은 요청을 수락한 직후, 첫 비동기 대기 전에 수행한다. 사전 검사도 같은 실행 시도에 포함하고, 검사 실패·설정 페이지 이동 등으로 실행이 종료되면 기본으로 복귀한다.
- 처리 중인 버튼의 툴팁/접근성 이름은 “게임 실행 취소”, 실행 중은 “게임 실행 중”으로 바꾼다.
- 세 아이콘 영역의 크기를 동일하게 유지한다. `ProgressRing.IsActive`는 처리 중에만 켜고, 표시 전환 시 버튼 크기는 유지한다.
- 기존의 추가 실행 직렬화 정책을 유지한다. 한 슬롯이 처리 중이면 그 슬롯만 취소용으로 활성이고, 다른 실행 버튼은 새 요청을 받지 않는다.
- 실패를 확정한 순간 기본 표시로 바꾸고, 이후 안내창이 닫힐 때까지 기다리지 않는다. 해당 시도의 늦은 로그인·소켓·프로세스 완료는 버튼 상태를 변경하지 않는다.
- 기존 5초 인증 재시도 제한은 표시 상태와 분리한다. 실패 즉시 play 표시로 복귀하되, 제한 중 새 실행 요청은 실행 검증에서 차단하고 남은 제한을 안내한다. 현재 제한이 UI 비활성화에 의존하는 부분은 서비스 검사로 보완한다.
- 세 슬롯은 서버와 무관한 전역 슬롯이라는 기존 정책을 유지한다. 서버/프리셋/선택 계정을 변경해도 진행·실행 중인 슬롯의 소유권이 바뀌지 않는다.

## 4. 구현 구조

### 4.1. MainWindow 수명의 실행 상태 소유자

MainWindow가 `GameLaunchCoordinator`를 생성하고 종료 시 정리한다. 세 슬롯의 표시 상태, 현재 실행 시도, 취소 토큰을 소유하고 `GameStarter` 상태 변경을 UI 스레드에 반영한다. 사이드바는 이 소유자의 슬롯 모델에 직접 바인딩한다.

HomePage의 실행 전 경로/계정/패치 검사와 안내 흐름은 재사용한다. HomePage에 남은 버튼 상태 속성·취소 코드는 새 소유자로 위임하거나 중복을 정리한다. 페이지 활성화/비활성화가 사이드바 실행 상태 구독의 수명을 결정하지 않도록 한다.

### 4.2. 실행 시도 식별과 선택값 고정

각 요청에 고유한 `AttemptId`와 취소 토큰을 부여한다. 서버, 슬롯 번호, 계정 ID, 설치 경로를 클릭 시점에 고정해 로그인 재진입, 소켓 수신, 런처 실행, 프로세스 탐색까지 같은 요청을 전달한다.

현재 `_launchAttemptVersion`은 초기화 후 일부 경로에서만 검사한다. 이를 전체 실행 시도에 연결하고, 비동기 대기 후와 각 부수효과 직전에 요청 유효성을 검사한다. 로그인 재진입에서 현재 `AppDataManager.SelectedServer`를 다시 읽어 요청의 서버/경로를 덮어쓰는 경로도 고정된 요청을 사용하도록 바꾼다.

### 4.3. 중단을 확정하는 공통 경로

`Fail(attempt, reason)` / `Cancel(attempt)`가 먼저 해당 시도를 종료 상태로 확정하고 기본 표시로 복귀시킨다. 이어서 필요한 자원을 정리한다.

- 해당 시도의 로그인/로그아웃 후속 실행과 WebView 탐색을 중단한다.
- 실행용 JavaScript 타이머와 로컬 소켓 대기를 정리한다. `CoreWebView2.Stop()`만으로는 이미 예약한 JavaScript 타이머까지 취소되지 않는다.
- 같은 시도의 `Starting` 예약과 프로세스 탐색만 취소한다.
- 취소 토큰을 `GameStarter.StartAsync`에도 전달한다. 소켓 대기용 10초 타임아웃과 실행 시도 전체의 취소 수명은 분리한다.
- 취소/실패/정리 콜백이 슬롯 번호만으로 다음 실행 시도를 제거하지 않도록 `AttemptId` 또는 동일 세션 참조를 검사한다.
- 이전 시도의 `StartAsync`가 `TryBeginStart`를 다시 호출해 취소된 슬롯을 새로 예약할 수 없도록, 새 요청 시작과 기존 요청 계속 실행을 구분한다.

### 4.4. 실행 완료와 실패의 경합

`GameStarter`의 세션과 상태 알림에 실행 시도 식별자를 연결한다. `Running` 승격은 그 세션이 현재 요청이고 아직 취소/실패하지 않았을 때만 허용한다. 기존 동일 세션 참조 검사를 유지하고, 시도 종료와 승격이 경합하면 먼저 확정된 결과만 반영한다.

게임 PID를 연결하면 실행 중으로 전환하고, 동일 시도/PID의 종료를 감지하면 기본으로 복귀한다. 실패 후 도착한 이전 이벤트는 새 요청의 상태를 잠그거나 초기화하지 못한다. 다른 계정/서버로 다시 실행할 때 이전 프로세스와 뒤늦은 payload가 새 요청에 잘못 연결되는 경우도 검증한다.

실행 준비 실패, 사용자 취소, 실제 실행 완료, 게임 종료를 구분한 결과와 원인을 통지한다. 세션이 사라졌다는 사실이나 `bool` 반환값만으로 결과를 추측하지 않는다. 이전 시도 정리는 해당 시도만 대상으로 하고, 새 시도의 정리나 실패 처리로 전달하지 않는다.

### 4.5. OTP와 공유 브라우저

- OTP 입력·재입력 대기 중에는 처리 중 표시를 유지한다. OTP의 “취소”와 “직접 입력”은 기존처럼 자동 게임 실행을 끝내고 기본으로 복귀한다.
- OTP는 모달 대화창이므로 표시 중에는 실행 버튼을 누를 수 없다. 이때는 기존 대화창의 취소 버튼이 같은 실행 취소 경로를 사용한다.
- 대기/표시 중인 OTP 대화창과 그 후속 제출은 해당 `AttemptId`에 연결한다. 시도가 종료되면 대기 중 OTP를 표시하지 않고, 이미 열린 해당 OTP도 정리하며, 늦은 입력 결과를 제출하지 않는다. 필요하면 공용 대화창 표시 API에 선택적 취소 토큰을 추가한다.
- 다른 게임 실행 및 BrowserButton/BrowserPage 계정 선택의 로그인 요청이 하나의 WebView2 상태를 동시에 바꾸지 않도록 공통 진행 검사로 보호한다. 기존 로그인 요청은 실행 취소 또는 완료 후 다시 사용할 수 있다.

## 5. 취소 범위

기존 `CancelLaunchAttempt`/`GameStarter.CancelStart`는 앱의 준비 작업과 추적을 취소하며, 이미 실행한 외부 `Run.exe`를 강제 종료하지 않는다. 이번 기본 계획도 강제 종료를 추가하지 않는다. 런처 호출 전에 취소되면 호출을 차단하고, 호출 후에는 앱의 후속 실행과 버튼 상태용 추적을 중단한다. 외부 런처가 이후 게임을 띄울 가능성은 있으나, 취소/실패한 시도의 완료 이벤트로 버튼을 실행 중으로 되돌리지 않는다.

이미 시작한 외부 런처가 남을 수 있으므로, 해당 런처와 뒤늦게 시작된 게임을 관찰하는 작업은 버튼 상태 처리와 분리해 유지한다. 발견한 프로세스는 최대 3클라이언트·동일 계정 중복 검사의 집계에 반영하고, 종료된 시도의 버튼을 `Running`으로 되돌리는 알림은 보내지 않는다. 실패 후 기본 표시를 유지하면서 실제 중복 실행 제한도 보존한다.

구현 시 보완: 취소된 런처의 게임 프로세스 탐색이 끝나기 전 새 실행을 허용하면 같은 경로의 늦은 PID를 새 시도에 연결할 수 있다. 따라서 이 기간에는 버튼을 기본 표시로 유지하되 새 요청을 사전 검증 및 서비스 예약 단계에서 차단한다. 게임이 발견되거나 런처 종료 후 기존 5초 탐색 유예가 끝나면 이 제한을 해제한다.

이미 호출한 런처 자체를 강제 종료하는 동작까지 원한다면 해당 시도의 런처 PID 종료 정책을 별도로 결정해야 한다. 실행 완료로 판정한 기존 게임을 취소 버튼으로 종료하는 동작은 요구사항에 포함되지 않는다.

## 6. 변경 대상과 순서

1. `Services/GameLaunchCoordinator.cs`: 시도/슬롯 상태 모델과 시작·취소·실패·완료 계약을 정의한다.
2. `Services/GameStarter.cs`: 현재 프로세스 판정을 유지하고 시도 식별·취소·상태 결과 통지를 보완한다.
3. `Services/WebViewManager.cs`: 고정 요청 전달, 전체 시도 유효성 검사, 공통 실패/취소 경로, 소켓·OTP 정리를 연결한다.
4. `MainWindow.xaml.cs`: 상태 소유자 수명과 요청 라우팅을 연결한다.
5. `Pages/HomePage.xaml.cs`: 기존 실행 전 검증을 재사용하고 중복 버튼 상태·취소 경로를 정리한다.
6. `Controls/SidebarView.xaml` / `.xaml.cs`: 세 실행 버튼의 play/ring/F0B9 바인딩, 토글 클릭, 툴팁·접근성 표시를 연결한다.
7. `Pages/BrowserPage.xaml` / `.xaml.cs`: 공유 로그인 요청이 진행 중 실행을 덮어쓰지 않도록 보호한다. OTP 대기 취소가 필요하면 `Diagnostics/ContentDialogCoordinator.cs`와 표시 확장 메서드를 함께 보완한다.

## 7. 검증 계획

- 세 슬롯에서 기본 → 처리 중 → 실행 중 → 게임 종료 → 기본 전환.
- 로그인 이전, OTP 이전, 소켓 대기, 런처 탐색 중 취소. 정상 취소를 오류 안내로 처리하지 않는지 확인.
- 무한 로그인 감지, 비밀번호 오류, OTP 취소/직접 입력, 소켓 시간 초과, UAC 취소, 런처 종료 후 게임 미감지 시 즉시 기본 복귀.
- 실패/취소 직후 재실행하고 이전 시도의 지연 완료·정리 이벤트가 새 요청을 변경하지 않는지 확인.
- Home/Browser/설정 전환, 서버/프리셋 변경 중에도 실행 상태와 취소 대상이 유지되는지 확인.
- 같은 버튼 연속 클릭은 새 실행 중복이 아니라 현재 시도 취소가 되는지 확인. 다른 슬롯/브라우저 로그인 요청과 충돌하지 않는지 확인.
- 기존 3클라이언트 제한, 계정 전역 중복 제한, 5초 재시도 제한 보존.
- Light/Dark/High Contrast에서 아이콘·ring 가독성과 동일 버튼 크기, 키보드 실행/취소와 접근성 이름 확인.
- 코드 구현 후 저장소 지침에 따라 Visual Studio MSBuild로 전체 `GersangStation.slnx` Debug/x64 빌드. 취소 경합 검증은 임시 코드로 수행하고 테스트 파일을 저장소에 추가하지 않는다. 실제 앱/게임 실행 검증은 사용자의 실행 요청이 있을 때 수행한다.

현재 조사에서는 Git 이력 및 소스만 확인했으며 앱·게임 실행이나 빌드를 수행하지 않았다. WinApp CLI가 현재 PATH에 없어 샘플 검색은 수행하지 않았고, 기존 GamePatchSettingPage의 WinUI ProgressRing 사용을 확인했다.

## 8. 구현 및 검증 결과

- `GameLaunchAttempt`가 선택 시점의 서버·슬롯·계정·경로와 취소 토큰을 고정한다. 전이는 준비/시작 → 실행 중 또는 실패/취소, 실행 중 → 종료만 허용한다. 실패/취소 후 늦은 완료는 거부한다.
- MainWindow 수명의 `GameLaunchCoordinator`와 세 슬롯 표시 모델에 사이드바가 바인딩한다. HomePage의 게임 상태 이벤트 구독과 중복 버튼 상태 코드는 제거했다. 현재 서버의 다클라 사용 설정은 런타임 상태와 별도로 전달한다.
- 로그인 재진입, 소켓 수신, 런처 예약·실행·프로세스 판정이 같은 시도를 사용한다. 정리에는 동일 시도/세션 참조 검사를 적용했다. 취소는 웹 탐색 및 소켓 대기를 중단하고 새 문서로 이동해 이전 스크립트 타이머를 폐기한다. OTP 직접 입력은 해당 문서를 보존한다.
- OTP 대기/표시와 재입력 카운트다운에 취소 수명을 연결했다. 공용 대화창 API의 선택적 취소 토큰은 대기 중 표시를 억제하고 열린 해당 대화창만 닫는다. 공유 브라우저의 별도 로그인은 초기화 대기부터 실행 요청과 직렬화한다.
- 취소된 외부 런처와 늦은 게임은 별도 세션으로 관찰하며 개수·계정 제한에 포함한다. 버튼을 실행 중으로 되돌리지 않는다. 외부 프로세스 강제 종료는 추가하지 않았다.
- 실제 상태 모델·GameStarter·대화창 조정기 소스를 연결한 저장소 밖 임시 검증이 449개 assertion을 통과했다. UI Dispatcher/WebViewManager/ContentDialog는 대역을 사용했다. 상태 전환, 첫 대기 전 표시, 같은 버튼 취소, 지연 결과·대기열 무시, 완료/취소 경합 200회, 슬롯/계정 전역 제한, 3개 제한, 재시도 제한, 수동 관찰 세션의 늦은 완료, 대기/표시 중 대화창 취소, 실행 중 사용 설정 변경 뒤 종료·취소를 검증했다. 실제 앱·게임·외부 런처는 실행하지 않았다.
- Visual Studio MSBuild의 전체 솔루션 Debug/x64 최종 빌드는 경고 0개·오류 0개로 통과했고 `git diff --check`도 통과했다. 실제 로그인/OTP 제출/소켓 통신/UAC/게임 시작·종료, 페이지 이동 중 표시, 테마 및 키보드 접근성은 실기 검증하지 않았다. 임시 검증 코드는 저장소에 추가하지 않았다.
