# WinUI app policies

Applies only to the matching feature in `GersangStation.WinUI/GersangStation/`. Core and Shared do not use these UI helpers.

## Failures and dialogs

- Reuse established handling for equivalent failures. Ask only when recovery, retry, fallback, termination, or presentation requires an unresolved product decision.
- Preserve original exception context. Expected failures need a meaningful result or recovery; cancellation is normally not an error.
- Common recoverable exceptions are logged immediately and announced with a non-modal main-window InfoBar; details open in a non-modal Drawer only on user request. Keep the last 20 notice records in memory without deleting log files, and preserve the currently read record when new failures arrive. The previous-run termination notice has independent state. Notification/viewer failures are logged only, without recursive dialogs or native fallback. Task-specific result UI and decision/OTP dialogs remain separate. Preserve the original cause and operation/target metadata of `AppDataOperationResult` failures without a generic failure dialog.
- Diagnostic Drawers wrap long lines and omit low-value process/thread, duplicate bitness, culture and directory metadata from recognized report headers. Preserve complete exception bodies, inner causes and unknown report formats. Keep original file logs and the original-copy action unchanged; display the log path separately rather than repeating its footer.
- Diagnostic logging and notice suppression are independent: forwarded instances of the same exception share one log, while a new equivalent exception gets its own log even if the short-window notice is suppressed. Keep shared browser-fault cascades coalesced, but announce a new browser request immediately.
- When a feature owns its failure UI, use `AppExceptionHandler.RecordRecoverable` for diagnostics without global UI; do not rethrow a handled failure solely to create a log. Browser data maintenance uses its page TeachingTip only, and logs without notifying after the page is left.
- Clone creation entry points share `MultiClientCreationService` and `MultiClientCreationFeedback`: identical success/cancel/failure messages, error icons, permission help and conflict-folder actions in their existing local TeachingTips. Record actual exceptions once in the shared service, not by opening an extra global exception dialog. Keep the pre-creation confirmation dialog.
- Installation results use the installation page's local TeachingTip and progress text, not result dialogs; permission failures offer an optional help action. Keep pre-install permission decisions and cancel/artifact choices as dialogs. Path-save failure after installation is a completion warning, not an installation failure or a second save-error dialog. Close results on accepted navigation/server changes and ignore stale progress callbacks after completion/cancellation.
- Install-path auto-save failures keep the entered path and show a persistent inline InfoBar with an explicit retry action, not a navigation-time failure dialog. Log each failed write once at the save boundary, including failed writes superseded by newer input; do not log it again in the install-completion caller. Keep existing pending-save navigation protection and clear the warning after a successful save or a return to the saved value.
- Install-path settings load failures use a page-local InfoBar with a reload action outside the disabled editor cards. Keep editing disabled until loading succeeds, never replace existing values with a failed read's defaults, and record each failed read without another global notice. Disable duplicate reloads while loading; successful reload restores editing without triggering auto-save.
- Account add/edit validation and save failures use the editor Drawer's inline InfoBar and retain all input. Record actual save/preparation failures once without a second global notice; validation is not a diagnostic error. Credential-service help opens externally without closing the editor. Clear obsolete feedback on retry/reset/new editing sessions; keep discard confirmation and delete/reorder/load flows separate.
- Account delete/order-save failures use the list's own InfoBar, with record-only diagnostics and optional external credential-service help. Preserve delete confirmation; failed deletion does not apply the candidate list. Restore the persisted account order and selection if reordering cannot be saved (including cancellation). Clear obsolete list feedback when an approved new operation begins; editor feedback remains independent.
- Account-list read failures retain the existing list/selection and block account mutation until a successful read. Show a persistent page-local notice with reload and optional credential-service help; these actions stay available independently of the blocked account editor. Log failures without a global duplicate notice, suppress concurrent reloads, and restore normal editing and surviving selection after successful recovery.
- Browser favorites are saved under the suggested page title before starting inline name editing. Enter/blur commits a trimmed nonempty name; Esc/empty input retains the last saved name (including a newly added default). Rename is available from the context menu and F2 without an input dialog. Commit candidate snapshots before changing visible data; save failure keeps the old data and rename draft with a page-local InfoBar and record-only diagnostics. Serialize add/delete/rename/favicon writes and reloads; background favicon failures stay quiet, and reload does not replace an active name editor. Keep corrupt-file reset confirmation separate.
- Favorites load/reset failures use a persistent browser-page recovery InfoBar and record-only diagnostics, independently of save feedback. Retain the current list on failed reads/writes and offer reload; expose reset only for a structured serialization failure. Never prompt automatically on load: reset requires an explicit action and a cancel-default destructive confirmation. Declining changes nothing; success alone clears the recovery state. Serialize recovery, suppress duplicate requests, and keep mutations blocked until recovery succeeds.
- Browser account-list read failures use their own persistent page InfoBar with reload and account-settings actions, without automatic dialogs/navigation or duplicate global notices. Retain the last list on failure but do not start a new login from it; keep browser navigation available and re-show the explanation on a new login attempt. Coalesce concurrent reads and align account selection with actual login state after successful recovery.
- Browser account/favorites recovery and favorites-save InfoBars are page-owned content hosted by the shell over the WebView area, not rows in the browser toolbar. Keep the toolbar's 8px padding; notifications never resize or shift it or the WebView. Collapse closed InfoBars themselves so stacked notifications have no empty gaps, and keep the overlay within the browser section's visibility lifetime.
- Browser-only login feedback targets the browser account ComboBox with a light-dismiss TeachingTip, not an InfoBar or failure dialog. Use Caution for missing passwords/retry limits and Critical for credential-store access errors/site login failures; offer account settings and credential-service help only when relevant. Keep account-list recovery separate. Clear pending/open tips on shell deactivation, unloading, disposal and a new login; ignore stale async results and defer popup reopening until the next UI turn after Closed. Preserve OTP/input/decision dialogs.
- Game-launch notices use that slot's actual ExecuteButton-targeted TeachingTip, with shared action/close lifetime and Light/Dark/HighContrast Signal Color resources. Missing selection/password, invalid/missing install paths, unreadable local version, patch requirements, cooldown, pending launcher detection, maximum-client count and duplicate accounts use Caution. Credential-store access errors and runtime authentication failures use Critical; record actual credential/version exceptions once without duplicate global guidance. Missing/blank passwords never delete accounts, change presets, or create diagnostic error records. Settings actions preserve the requested server (patch navigation uses its patch-specific parameter); the unified install/path page needs one navigation action. Never navigate automatically.
- Capture the GameLaunchAttempt before runtime-login failure cleanup clears browser caches; only its still-current failed slot may receive the notice. Browser-only login notices remain separate. Clear old tips on accepted launch/server changes, settings navigation, and unloading; ignore late action failure feedback after dismissal/retry and log it only. Action failures use the same tip, not another global/dialog notice. Keep OTP input, clone-creation approval, and the latest-version-unavailable continue/cancel decision as dialogs.
- Patch failures use one result TeachingTip, including permission failures with an optional help action. Record patch/install exceptions independently of guidance, including failed cleanup and patch-history operations. Declining a corrupt-data reset ends that prompt without another load-failure dialog; a failed approved reset remains a separate failure.
- Patch settings read failures stop preparation/start and use the patch page's TeachingTip with record-only diagnostics; never continue with failed-read defaults. Archive reuse remains an explicit resume/restart/cancel decision, and cancel must stop before worker creation or archive cleanup. Busy install/patch/clone navigation refusals use local TeachingTips rather than acknowledgement dialogs.
- Developer version edits use structured settings reads and button-targeted TeachingTips for validation/results. Record actual failures, prevent duplicate writes while loading, and do not write after leaving the page before the read completes.
- Phone-verification guidance preserves the verification document, ends the pending launch without a retry cooldown, and offers an explicit browser action on the original launch slot or browser account ComboBox. Do not auto-navigate. OTP dialogs and retry/input logic remain unchanged.
- Browser session faults are not normal cancellation. Preserve their original cause and coalesce the fault notification with interrupted in-flight operations; a new user request after the fault receives a fresh explanation. Do not add fault-based button disabling. Keep normal request replacement, maintenance suspension and disposal cancellation separate; do not globally reinterpret cancellation exceptions.
- Maintenance cancellation requires an identified reason: before-start cancellation, UAC refusal, or worker-confirmed cancellation requested by the app. Connection timeout, lost IPC, and unrequested worker cancellation are failures even when a user cancellation overlaps them. Preserve the write gate until the worker exits. After patch application succeeds, temporary-file cleanup is best effort; send cleanup diagnostics to the app for logging only, without changing patch success or showing an extra warning.
- At throwing app boundaries, use `TryEnqueueHandled`, `FireAndForgetHandled`, `SafeExecution.RunHandledAsync`, or `SafeExecution.StartHandledTimer` as appropriate.
- Prefer explicit `AppExceptionHandler` intent methods over the legacy boolean API. Fatal UI/startup boundaries use `FatalErrorHandler`: best-effort recording with a bounded wait, then process termination, without XAML, dispatcher scheduling, dialog gates, or normal cleanup. The terminating `AppDomain` hook only attempts bounded recording and lets the CLR terminate. A recorded crash is announced non-modally on the next primary-instance startup; details open in a non-modal Drawer only on user request.
- Guard native/WinRT callback bodies so exceptions do not cross the ABI without a managed report. `AppSessionJournal` records primary-instance start and accepted normal exit as a fallback for native fail-fast/forced termination. An incomplete previous session is announced as an unknown termination, not an invented exception; prefer the matching captured fatal report when available. Do not mark close cancellation, tray hiding, or a secondary-instance redirect as a completed session.
- Show dialogs with `ShowManagedAsync` through `App.DialogCoordinator`; reusable dialogs derive from `AppContentDialog`.

## Navigation and startup

- Shell navigation and user-requested exit share the content-transition gate. Await leave/save decisions before changing frames, browser documents, or sections; `OnNavigatingFrom` is a synchronous safety guard, never an asynchronous confirmation. A pending exit rejects new navigation and invalidates queued navigation. Failed exit validation keeps the window open and uses recoverable exception handling.
- Tray Exit restores and foregrounds the main window, then uses the same page-work, unsaved-edit and exit confirmation as an ordinary close. Close-to-tray does not request exit; installed Store-update termination remains an explicit forced-close path. Account writes block departure, and account editor departure reuses the Drawer's discard confirmation without discarding drafts when exit is cancelled.
- App web links normally open in the internal WebView unless OS browser handoff is required.
- Automatic startup uses the package's `GersangStationStartup` task through `Windows.ApplicationModel.StartupTask`. Read Windows state without changing it when loading settings; respect user-disabled and policy-controlled states. Do not create elevated scheduled tasks, PowerShell launchers, or administrator shortcuts. Existing legacy scheduled tasks are cleaned up manually, not migrated or deleted by the app.
- Validate actual logon activation separately from compilation. Main-app startup remains `asInvoker`; elevation for the on-demand game maintenance worker and advanced-feature permission checks are separate policies.

## Packaged links and policy assets

Paths below are repository-relative.

- Privacy text: `GersangStation.WinUI/GersangStation/Assets/Policies/`; keep the app link aligned when it changes.
- Help/policy/license URLs: `metadata/winui-links-manifest.json`. Remote values override the packaged default; missing remote keys fall back to it, then to the HTML error page if neither supplies a value.
- Store fallback: `metadata/winui-store-update-version-manifest.json` is a cumulative history of `"{version, required}"` strings, read remotely for manual-help fallback after Store detection/install failures.
- Shell-visible package names use resources under `GersangStation.WinUI/GersangStation/Strings/`.

Package builds and Store draft edits use the [release procedure](../../docs/winui-store-release.md); ordinary asset edits do not start that workflow.
